> **Continuing development? Read [DEVLOG.md](DEVLOG.md) first.**

Research project analyzing the correlation between animal abuse and subsequent violent crimes through judicial judgment data analysis.

## Project Overview

This project aims to verify and present the phenomenon that animal abuse often correlates with or precedes serious violent crimes, enabling early warning systems when an individual shows both criminal behavior and animal abuse records.

**Data Source**: Judicial Yuan Open Data Platform (Taiwan)
**Data Range**: 1996.01 - 2026.07 (367 monthly packages)
**Data Volume**:
- Raw: ~52GB compressed RAR files, ~150GB extracted JSON
- Processed: 7.73 million criminal cases (1.2GB CSV + 12GB Parquet)

## Quick Start

### Option 1: Use Processed Data (Recommended)

```bash
# 1. Setup environment
cd project_aepa
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 2. Get processed data (28.5 GiB, 13,043 files)
#    This does NOT work yet: the Drive remote is empty and the account holds
#    15 GB, half of what the data needs (DEVLOG, 2026-11-26). Copy data/processed
#    from a machine that has it instead.
dvc pull
```

**Data includes:**
- **CSV**: 7.73 million criminal case summaries (without full judgment text)
- **Parquet**: Complete judgment data with full text (batch files)

```bash
# 3. Secret key for hashing defendant names
cp .env.example .env   # then set NAME_HASH_KEY
```

`NAME_HASH_KEY` must be identical on every machine (copy it by hand, e.g. via a password
manager; never commit it). A different key gives different name hashes, and data built on
two machines will no longer link. Never change it once data has been built.

### Where data lives

| Data | How it moves between machines |
|---|---|
| Code, `data/labels/` (human labels) | git |
| `data/processed/` (28.5 GiB) | copied by hand; the Drive remote is empty and too small, see DEVLOG 2026-11-26 |
| `data/verified/` (LLM labels; ~31 h to redo) | DVC after the full run (`dvc add data/verified`, `dvc push`) |
| `.env` (`NAME_HASH_KEY`) | copied by hand |
| `.dvc/config.local` (Google Drive OAuth client) | created per machine, see below |
| `data/structured`, `index`, `filtered`, `analysis` | regenerated by scripts (see DEVLOG *Commands*) |
| `data/raw/` (52 GB RAR) | not needed once `data/processed` is pulled |

LLM labels from a different model (e.g. a non-MLX model on a non-Mac machine) must be kept
separate from existing ones.

### Google Drive access for `dvc pull`

DVC ships a default Google OAuth client that Google has shut down, so every machine needs
its own client ID and secret before `dvc pull` can reach the remote. The credentials go in
`.dvc/config.local`, which is never committed, so a fresh clone always needs this once.

**Prerequisites:** a Google account that can open the remote folder, and a browser on your
own computer.

* Create a Google Cloud project, then select it in the top bar.

```
https://console.cloud.google.com/projectcreate
```

* Enable the Google Drive API for that project. Check the project name in the top bar
  first; enabling it on the wrong project is the most common mistake here.

```
https://console.cloud.google.com/apis/library/drive.googleapis.com
```

* Configure the OAuth consent screen. Pick **External** unless you are on a Workspace
  account, and fill in the app name and your own email for both contact fields.

```
https://console.cloud.google.com/auth/overview
```

* Add the Google account that owns the remote folder under **Test users**. Skipping this
  gives a 403 at sign-in, after everything else looks correct.

```
https://console.cloud.google.com/auth/audience
```

* Create an OAuth client with application type **Desktop app**, and copy the client ID and
  secret from the dialog. Desktop clients accept any `http://localhost` port, so there are
  no redirect URIs to register.

```
https://console.cloud.google.com/auth/clients
```

* Store both values. `--local` writes them to `.dvc/config.local`, outside git.

```bash
dvc remote modify --local gdrive gdrive_client_id '<client id>'
dvc remote modify --local gdrive gdrive_client_secret '<client secret>'
```

* On a headless machine, forward the callback ports from your own computer and keep the
  connection open until the pull finishes. DVC serves the OAuth callback on port 8080,
  falling back to 8090; without the forward, sign-in completes in the browser and the
  server waits forever.

```bash
ssh -L 8080:localhost:8080 -L 8090:localhost:8090 <user>@<host>
```

* Pull the data. DVC prints `Go to the following link in your browser:` and a URL; open it
  on your own computer and sign in. Google warns that the app is unverified, which is
  normal for a Testing-mode client: choose **Advanced**, then **Go to (app name)
  (unsafe)**, then **Allow**.

```bash
dvc pull
```

* Confirm the file count matches `nfiles` in `data/processed.dvc`.

```bash
ls data/processed | wc -l    # 13043
```

The token is cached under `~/.cache/pydrive2fs/`. While the OAuth app stays in Testing
mode Google expires refresh tokens after 7 days; when a later `dvc pull` fails to
authenticate, delete that directory and sign in again.

### Rebuilding derived data on a new machine

Everything except `data/processed` (DVC) and `NAME_HASH_KEY` (copied by hand) is rebuilt
by scripts; the commands are in DEVLOG *Current State → Commands*. The scripts are
deterministic: the same `data/processed` gives the same outputs, including the `--test`
samples.

### LLM server (Stage 3)

vLLM is not in `requirements.txt` because its install differs by platform. Install it in
its own virtual environment (it pins its own PyTorch):

| Platform | Install | Model |
|---|---|---|
| Linux + NVIDIA GPU | `pip install vllm` | `Qwen/Qwen3-8B` |
| macOS (Apple Silicon) | vLLM with the vllm-metal plugin (follow its README) | `Qwen/Qwen3-8B-MLX-4bit` |

```bash
vllm serve <model> --max-model-len 8192 --port 8000
```

The model downloads from Hugging Face on first start. Labels from different models are
written to different files (the model name is part of the file name).

## Research Design

This project uses a **retrospective approach** rather than prospective tracking:

**Research Question**: Among individuals who have committed violent crimes, what percentage have a history of animal abuse?

**Methodology**: Extract prior conviction narratives from criminal judgments, as judgments typically contain the defendant's criminal history within a single document.

**Cross-judgment linking**: Defendant names are masked before ~2011 but public afterwards,
so judgments from 2011 on can be linked through cited prior case numbers and hashed
defendant names (see DEVLOG, 2026-11-23).

For detailed research design, see [animal-abuse-crime-linkage-data-plan.md](animal-abuse-crime-linkage-data-plan.md).
